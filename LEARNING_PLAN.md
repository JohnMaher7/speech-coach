- **Stage 23 (revisit — shipped single-pass)** — stress-tested the two-pass design against the *product* question (does this make the eval better?) and against the *cost* numbers, found both pointed the other way for our input size, and reverted to single-pass: (1) **schema as filter** — a fixed-shape digest (`Evidence`) is a lossy compression of the transcript; whatever Haiku doesn't surface, the judge can't comment on, so phrase-level rewrites, pattern critique ("you say 'literally' six times"), weak-verb / hedge detection, and word-choice feedback all become structurally impossible regardless of how good Sonnet is — quality bottlenecks are often shape constraints, not model capability; (2) **measured cost flipped the case** — two-pass ≈ $0.0162/report (extract $0.0025 + synthesize $0.0137) vs single-pass ≈ $0.013/report on the same inputs, because the cheap-extractor-saves-money math only pencils out when the cheap model's job is *digesting a huge input* and our 200-1400-token speeches don't qualify (Haiku's own system-prompt + output-token overhead exceeds what Sonnet would have paid to read the transcript directly); (3) **the right way to ship `cost.py`** — pricing telemetry is independent of the pipeline shape, so it stayed, while `LlmCost` collapsed from `{extract_usd, synthesize_usd, total_usd}` to `{total_usd}` and old persisted reports keep validating because Pydantic's default config ignores unknown payload keys (pinned by a new back-compat test that would break loudly on any future `extra="forbid"` regression); (4) **adaptive thinking forced a structured-output mechanism change** — `thinking={"type":"adaptive"}` on Sonnet 4.6 lets the model deliberate before scoring, but `thinking` + `tool_choice={"type":"tool",...}` returns a 400 ("Thinking may not be enabled when tool_choice forces tool use"), so `synthesize()` moved from forced tool-use to **structured outputs** (`output_config={"format":{"type":"json_schema","schema": Synthesis.model_json_schema()}}`) — the JSON now comes back in a text block (ThinkingBlocks precede it; the extraction loop just looks for `block.type == "text"` and `json.loads` it), `max_tokens` raised 2048 → 8192 so neither the reasoning nor the report truncates, and structured outputs needed two schema tweaks: `model_config = ConfigDict(extra="forbid")` on every output model (it requires `additionalProperties: false`) and `CategoryScore.score: Literal[1,2,3,4,5]` instead of `Field(ge=1, le=5)` (it rejects `minimum`/`maximum` on integers but accepts `enum`) — the bonus is server-side schema enforcement that killed the occasional malformed-output flake tool-use had; (5) **a richer output schema** — a new `Synthesis.rewrites: list[Rewrite]` (`{original, suggested, why}`) field forces line-level evaluator-style feedback grounded in verbatim phrasings, with eval tests asserting every `original` is a (whitespace-normalised) substring of the transcript so the model literally cannot invent phrasings the speaker didn't say; the lesson worth keeping in muscle memory: **measure cost on real inputs before committing to a pattern, check whether your schema can even *express* the feedback you want before blaming the model, and expect API features to constrain each other (forced tool-use ⊥ adaptive thinking; structured outputs ⊥ numeric `minimum`/`maximum`)**.

- **Stage 23 (original — two-pass)** — split a monolithic LLM call into a **two-pass extract → synthesize** pipeline: a cheap, mechanical first pass (`extract_evidence` on Haiku 4.5) reads the raw transcript and forces a `submit_evidence` tool call returning a fixed-shape `Evidence` digest (opening / closing / thesis / signposts / notable_quotes / filler_examples), then an expensive, careful second pass (`synthesize` on Sonnet 4.6) judges against the *digest* — never the raw transcript — so the smart model's input no longer scales with speech length, the few-shots get rewritten to show `Evidence: {...}` (not `Transcript: "..."`) because few-shot inputs must match the real input shape, and you gain a debuggable middle layer (a wrong rationale is now traceable to extraction-missed-it vs synthesis-misjudged-it); pick the cheapest model that does the job (mechanical extraction → Haiku at ~1/3 Sonnet's price; nuanced judgement → Sonnet) rather than reaching for the biggest by reflex; do the **cache ROI math** out loud — a cache *write* is 1.25× normal input price and a *read* is 0.1×, so the cached prefix is net-positive after the second request and nearly halves input cost after ten, while a sub-floor prefix (Haiku's 4096-token / Sonnet's 2048-token minimums) silently never caches (the extract prompt's `cache_control` marker is wired but inactive — same as stage 11's pre-few-shot Sonnet prompt); centralise pricing in `app/cost.py` (`ModelPricing` dataclass + `PRICING` dict keyed by model ID + `usage_cost(model, usage)`) with the one trap pinned by a unit test — `usage.input_tokens` is the *uncached remainder*, so cache writes and reads are billed *on top of it* at their own multipliers and pricing a call by `input_tokens` alone undercounts every cached request; thread the per-call cost back out (`extract`/`synthesize` now return `tuple[Result, float]`), sum it into a persisted `LlmCost` on the `Report`, log the per-report total, and surface "$0.00XX to generate" on the report page — a number you can see is a number you can optimise.

- **Stage 22** — close the AI-engineering loop with **few-shots + an eval harness**: convert the rubric-only system prompt into a *show-don't-tell* prompt by appending two `<example>` blocks (one fillery+fast+monotone+weak-structure scoring 1/2/2/2, one clean+well-paced+monotone+strong-structure scoring 5/5/2/5) so the model learns *tone of rationale* and *specificity of top-action* by pattern match rather than rule parse — and as a side effect push the cached prefix from ~1500 to ~2507 tokens, finally clearing Sonnet 4.6's 2048-token cache floor (verify with `usage.cache_read_input_tokens > 0` from the second call onwards, which is exactly what the eval harness's 3 sequential calls demonstrate: `cache_create=2507/read=0`, then `cache_create=570/read=2507`, then `cache_read=2507`); build a real **golden set** in `tests/fixtures.py` as 3 hand-crafted `(Transcript, Metrics)` pairs covering distinct rubric corners (fillery_fast, clean_paced, monotone_structured) — kept *separate* from the few-shot examples (otherwise eval tests memorisation, not generalisation); write **behavioural assertions** as score *bands* (`fillers.score <= 2`, not `== 1`) and rationale *concept* matches (`"pitch" in vocal_variety.rationale.lower()`) to leave the model room to wobble within a class, while skipping structural assertions (Pydantic already caught those at parse time); learn **pytest** fundamentals — `@pytest.fixture` for shared setup auto-injected by parameter name, `tests/conftest.py` as the home for fixtures available to every test file, `@pytest.mark.eval` + `addopts = "-m 'not eval'"` so `uv run pytest` runs the free unit tests on every commit while `uv run pytest -m eval` opts into ~$0.02 of real Claude calls, and `asyncio_mode = "auto"` from `pytest-asyncio` so `async def test_...` runs on an event loop without per-test decoration; and write the unit tests at the *bug-bait lines* from stages 14-15 — WPM-window edge clipping (`width = window_end - window_start`), monotone score clamping at the 0/1 bounds, long-pause threshold semantics — so refactors of the metrics pipeline never silently regress those calibrations.

- **Stage 25** — close the loop with the operational hardening pass that turns "works on my machine" into "safe to put on a CV": (1) **rate limiting with slowapi** — a decorator-shaped, IP-keyed limiter (`Limiter(key_func=get_remote_address)`) attached via `app.state.limiter = limiter` + `app.add_exception_handler(RateLimitExceeded, ...)`, with `@limiter.limit("5/hour;20/day")` on `/analyze` and `@limiter.limit("30/minute")` on `/uploads/sign` — knowing `request: Request` must now be the first route parameter (slowapi inspects the signature for it), the decorator order matters (`@app.post` outermost, `@limiter.limit` closer to `def` — Python applies bottom-up so the limit wraps the raw function and FastAPI registers the wrapped version), stacked limits via `;` enforce *both* caps (burst-protect hourly + abuse-protect daily), and the default 429 body is `{"error": "..."}` not `{"detail": "..."}` so a custom handler returning the latter is needed for the frontend's existing `(await res.json()).detail` path to surface a real sentence instead of `HTTP 429`; pick rate-limit values from real cost math (at $0.013/report × 20/day max per IP = $0.26/day per abuser, annoying not ruinous), accept the in-memory store's multi-process limitation for a portfolio tool (Redis swap is one constructor arg if it ever matters); (2) **Sentry via `sentry-sdk[fastapi]>=2.20.0`** — `sentry_sdk.init(dsn=settings.sentry_dsn, environment="production", traces_sample_rate=0.1, send_default_pii=False)` at module top *before* `FastAPI(...)` is constructed (the FastAPI integration installs middleware at app-construction time — too late if init runs after), wrapped in `if settings.sentry_dsn:` so local dev is a no-op (otherwise every iteration-loop traceback floods the free-tier quota), and recognising that the **logging integration is the unsung hero** of this wiring — by default it captures `logging.ERROR` and above as Sentry events with stack traces, so our existing stage-21 `except Exception: logger.exception("analyze stream failed for key=%s", req.key); yield sse_event("error", ...)` pattern *automatically* generates a Sentry event without any code change (without it, our caught-and-logged exceptions would be invisible to the FastAPI integration which only sees uncaught exceptions); (3) **Modal `min_containers=1`** as the single biggest perceived-quality win — flipping the function decorator from `@app.function(secrets=...)` to `@app.function(secrets=..., min_containers=1)` keeps one container always warm, killing the 1–3 s cold start the first user of the day would pay (idle containers bill at a much lower per-second rate than active ones — ~$8-10/mo for a 0.125 vCPU container 24/7, fits the $30/mo free tier); (4) **a stdlib-only smoke test in `scripts/smoke.py`** that hits `/health` + `/uploads/sign` on the live URL and asserts 200/shape — runs in ~1 s, costs nothing, catches the post-deploy nightmare class (missing env var → `Settings()` fails at import, syntax error in newly-shipped code, broken CORS preflight) *before* a real user does, and deliberately *doesn't* upload audio because that would burn Deepgram + Claude every deploy (the full E2E stays as a manual launch-checklist step); and (5) the underlying lesson — **the operational layer wrapped around a working pipeline is a separate skill** from building the pipeline, and it lives almost entirely in config (decorators, env vars, secrets, deploy flags) rather than logic, so it reads "small" but is what separates a tutorial project from one that can withstand its first hostile visitor.

- **Stage 24** — give the whole app a *design system* instead of styling every page by hand: in Tailwind v4 you don't have a `tailwind.config.js` — you declare **design tokens** as CSS variables inside `@theme` (or `@theme inline`) in `globals.css`, and Tailwind turns each `--color-X` into a family of utilities (`bg-X`, `text-X`, `border-X`, `ring-X`, plus opacity modifiers like `bg-X/12`); so adding `--score-good`/`--score-mid`/`--score-low` once made `text-score-good` etc. real classes everywhere, and switching `--primary` from neutral grey to indigo re-skinned every button, ring, and accent in one edit (also: a token that points at itself — `--font-sans: var(--font-sans)` — is undefined, so the Geist font never applied until it pointed at `--font-geist-sans`); wrap every page in shared **chrome** by rendering `<SiteHeader/>{children}<SiteFooter/>` from `app/layout.tsx` with `body` as `flex min-h-svh flex-col` and the footer pinned by `mt-auto` — and keep header/footer as **Server Components** because they have zero interactivity, so they ship as plain HTML with no client JS (each page now owns the single `<main>`, since nesting `<main>` is invalid); build a tiny **composition vocabulary** — hand-rolled `Card`/`Badge` in the same `cn`/`cva` idiom as the existing `button.tsx` (cheaper and more consistent than re-styling a `<div>` on every page), plus a `lib/scores.ts` that maps a 1-5 score to a tone (`good`/`mid`/`low`) and an overall to a one-word verdict, with the tone→Tailwind-class maps written as **string literals** so Tailwind's source scanner actually emits those classes (a `text-${tone}` template would be invisible to it); use an icon set (`lucide-react`) for product polish — `import { UploadCloud, AudioWaveform, ... } from "lucide-react"`, typed as `React.ComponentType<{ className?: string }>` so it can be passed around in data arrays (lucide v1 doesn't export a `LucideIcon` type); design the **report page for visual hierarchy** — a tone-coloured ring around the overall score, a coloured `Badge` + a 5-segment meter bar on each rubric card so a "4" *looks* good and a "2" *looks* weak, a "what you said → try instead → why" treatment for rewrites, the chart in a titled `Card`, incidental numbers and raw JSON tucked into a `<details>` at the bottom; upgrade the timeline chart from `LineChart` to recharts' `ComposedChart` so the pitch series can be an `Area` with a `<defs><linearGradient>` fill (plain SVG elements rendered inside the chart) while WPM stays a `Line`; and remember that **branding is part of the product** — renamed the app *Rhetor* (the classical word for a teacher of oratory) and stripped "Toastmasters" from every user-facing surface *and* the LLM system-prompt persona (which costs one cache *write* on the next call, no behaviour change), because a portfolio piece that still wears someone else's org name isn't finished.
